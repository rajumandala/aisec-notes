## What changes in an AI architecture review

You already know how to review an architecture: draw the data flows, mark the trust boundaries, find threats, check controls. All of that still applies. Four things are new:

| Classic review | AI review |
|---|---|
| Code follows rules you can read | The model follows instructions, and **any text it reads can be an instruction** |
| Input is data | Input to the model is data **and** possible instructions |
| A component's output is trusted if the component is trusted | **Model output is always untrusted input** to whatever uses it next, even when the model provider is trusted |
| Behaviour is fixed until the code changes | Behaviour changes with the prompt, the model version and the data, even when the code does not |

## The review in six steps

### 1. Describe the system

| Question | Example answer |
|---|---|
| What is it for, and who uses it? | Helpdesk analysts ask questions about tickets and close duplicates |
| What can it do on its own? | Read tickets, search the knowledge base, close tickets after approval |
| Which model and provider? Which version? | `gpt-6-luna` through the OpenAI API |
| What data does it handle, and how sensitive is it? | Ticket text, which may contain personal data |
| What does the provider keep, and for how long? | Check the provider's data retention and training terms |

### 2. Draw the data flow, including the AI parts

Besides the usual users, services and databases, draw: the **model**, every **tool**, every **data source** whose text reaches the model (tickets, documents, web pages, MCP servers), **memory**, **other agents**, and **logs and traces**.

### 3. For every piece of text that reaches the model, ask who can write it

This is the most important step. If someone can write it, they can try to instruct the model.

| Text reaching the model | Who can write it | Trusted? |
|---|---|---|
| System instructions | Your developers | Yes |
| The analyst's question | The signed-in analyst | As much as that analyst |
| Ticket text | **Anyone who can raise a ticket** | No |
| Knowledge base articles | **Any employee who can edit the wiki** | No, unless only reviewed articles are indexed |
| MCP tool descriptions | **The server's author** | Only after review and hash pinning |
| Saved memories | Whatever produced them, possibly ticket text | Only if built from the user's own words |
| Another agent's message | Whatever that agent read | No |

### 4. For every tool, ask what it can change and as whom

| Tool | What it can change | Whose identity it uses | Approval? |
|---|---|---|---|
| `get_ticket` | Nothing (read only) | The signed-in user, from the session | No |
| `close_ticket` | Ticket status | The signed-in user, from the session | Yes, showing the ticket and the reason |
| `send_email` | Sends data out of the system | ? | ? |

Any "?" is a finding.

### 5. Look for the known dangerous combinations

| Check | Question |
|---|---|
| Data theft | Does any single session have private data, untrusted text **and** a way to send data out? (Concept 10) |
| Excessive agency | Can the model choose the target of an action, such as which account to reset? (Concepts 2 and 9) |
| Identity | Does any tool take the user's identity from a model argument? (Concept 3) |
| Limits | Are there step, cost and time limits in code? What happens when they are reached? (Concept 4) |
| Retrieval | Is access checked in code before documents reach the model? (Concept 7) |
| Persistence | Can untrusted text become a saved memory? (Concept 8) |
| Code execution | Does model-written code run anywhere outside a sandbox? (Concept 9) |
| Third parties | Which MCP servers, frameworks and models are used, pinned to which versions? (Concepts 6 and 11) |
| Logs | Do traces or logs copy sensitive data to a third party? (Concept 11) |

Then go through both OWASP lists (LLM Top 10 and Agentic Top 10) to check that nothing was missed.

### 6. Ask for evidence, not promises

| Claim | Evidence to ask for |
|---|---|
| "The model resists prompt injection" | Eval results with security cases and pass rates (Concept 5), and red team results (Concept 10) |
| "Users only see their own data" | The code of the access check, and a test showing one user cannot see another's data |
| "Actions need approval" | The approval code, showing the exact approved action is the one that runs |
| "We monitor it" | What is logged, who reviews it, and what triggers an alert |

"The prompt tells the model not to do that" is not evidence of a control.

## Example findings

| # | Finding | Risk | Recommendation |
|---|---|---|---|
| 1 | Ticket text and the `send_email` tool are in the same session as other users' tickets | Data theft through injected ticket text | Remove `send_email`, or allow emails only to the signed-in user |
| 2 | The MFA reset target is taken from the reader agent's note | Any user can reset another user's MFA | Take the target from the ticket's requester field |
| 3 | The knowledge base index has no access filter | HR-only articles reach every user | Filter by the user's groups before retrieval |
| 4 | Agent framework tracing is on with sensitive data | Ticket text copied to a third party | Turn tracing off, or exclude data from traces |
| 5 | No eval exists for the current model version | A model update could change behaviour unnoticed | Add an eval with security cases and run it on every change |

## Summary

| Lesson | Example |
|---|---|
| Classic review methods still apply, with the model added as a component | Draw the model, tools, data sources, memory and traces |
| Ask who can write each text that reaches the model | Anyone can raise a ticket, so ticket text is untrusted |
| Model output is always untrusted input to the next step | The reader agent's note is not a trusted instruction |
| Ask what each tool can change and as whom | Identity comes from the session, never from the model |
| Ask for evidence, not promises | Eval and red team results, not "the prompt says so" |
