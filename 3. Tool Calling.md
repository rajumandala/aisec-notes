## Part 1: The concept

### What tool calling is

Until now the model could only return text: a summary, or a filled-in `TicketTriage`. It could not look anything up or do anything.

**Tool calling** lets the model ask your program to run a function. You describe the functions it may ask for. When the model needs one, it does not answer the user. Instead it returns a structured request such as:

```
call get_ticket_status with {"ticket_id": "T-101"}
```

Your code reads that request, decides whether to run the function, runs it, and sends the result back. The model then writes its answer using that result.

### The flow

| Step | Who does it | What happens |
|---|---|---|
| 1 | Your code | Sends the user's question **and** a list of tool descriptions to the model |
| 2 | The model | Returns a tool call: a tool name and arguments, as JSON. It runs nothing |
| 3 | Your code | Reads the tool call, runs the real function (or refuses), and sends the result back |
| 4 | The model | Reads the result and writes the answer for the user |

> **The model never runs anything.** Every tool call passes through your code in step 3. That step is the control point, in the same way that an API server is the control point for every request from a browser.

### A tool has two separate parts

| Part | What it is | Who sees it |
|---|---|---|
| **Tool description** | A name, a sentence explaining what it does, and a JSON schema for its arguments | The model |
| **Function** | Ordinary Python code that does the work | Only your program |

The model sees the description only. It cannot see or change the function. Your code links the two: when the model asks for `get_ticket_status`, your code decides which function runs.

### AppSec equivalent

| Web application | Tool calling |
|---|---|
| The browser sends `GET /tickets/T-101` | The model returns `get_ticket_status {"ticket_id": "T-101"}` |
| The URL and parameters come from the client, so they are untrusted | The tool name and arguments come from the model, so they are untrusted |
| The server decides whether to serve the request | Your code decides whether to run the function |

This is Concept 2 again: **the model proposes, code decides.** A tool call is a proposal to run a function.

### What can go wrong (covered in later parts)

| Risk | Short description |
|---|---|
| **Who may call which tool** | The model can ask for anything its tools allow, including another user's data. Authorisation must use the signed-in user's identity, not the model's arguments |
| **Input checks** | Arguments are model output. They need the same validation as any untrusted input |
| **Instructions hidden in tool results** | Tool results are sent back into the model's input. If a result contains text written by someone else, that text can carry instructions |

## Part 2: Worked example

File: `src/ai_appsec/ticket_status_tool.py`

```python
import json

from dotenv import load_dotenv
from openai import OpenAI

load_dotenv()

client = OpenAI()

# Simulated ticket system (trusted data).
TICKETS = {
    "T-101": {"owner": "asha@example.com", "status": "open", "assigned_to": "access team"},
    "T-102": {"owner": "ravi@example.com", "status": "resolved", "assigned_to": "hardware team"},
}


def get_ticket_status(ticket_id: str) -> dict:
    """The real function. Only our code can run it."""
    ticket = TICKETS.get(ticket_id)
    if ticket is None:
        return {"error": "ticket not found"}
    return {"ticket_id": ticket_id, "status": ticket["status"], "assigned_to": ticket["assigned_to"]}


# The description of the tool that the model sees. It is not the function itself.
TOOLS = [
    {
        "type": "function",
        "name": "get_ticket_status",
        "description": "Look up the current status of a helpdesk ticket by its ID.",
        "parameters": {
            "type": "object",
            "properties": {
                "ticket_id": {"type": "string", "description": "The ticket ID, for example T-101"},
            },
            "required": ["ticket_id"],
            "additionalProperties": False,
        },
        "strict": True,
    }
]

INSTRUCTIONS = "You are a helpdesk assistant. Use the tools to answer questions about tickets."

conversation = [{"role": "user", "content": "Hi, what is happening with my ticket T-101?"}]

# Round 1: the model decides whether to ask for a tool.
response = client.responses.create(
    model="gpt-6-luna",
    instructions=INSTRUCTIONS,
    input=conversation,
    tools=TOOLS,
)
conversation += response.output

for item in response.output:
    if item.type != "function_call":
        continue
    print("Model asks for:", item.name, item.arguments)
    arguments = json.loads(item.arguments)
    if item.name == "get_ticket_status":
        result = get_ticket_status(arguments["ticket_id"])
    else:
        result = {"error": "unknown tool"}
    print("Our code returns:", result)
    conversation.append(
        {"type": "function_call_output", "call_id": item.call_id, "output": json.dumps(result)}
    )

# Round 2: the model writes the answer using the tool result.
response = client.responses.create(
    model="gpt-6-luna",
    instructions=INSTRUCTIONS,
    input=conversation,
    tools=TOOLS,
)
print("Answer:", response.output_text)
```

### Line-by-line explanation

| Code | What it does |
|---|---|
| `import json` | Python's built-in JSON library. Tool arguments arrive as JSON text and must be converted into a Python `dict` |
| `TICKETS = {...}` | Simulates the ticket system: a `dict` that maps each ticket ID to its details. Each ticket has an `owner` |
| `def get_ticket_status(ticket_id)` | The real function. It looks up the ticket and returns only `status` and `assigned_to`, not the whole record |
| `TICKETS.get(ticket_id)` | Returns the ticket, or `None` if the ID does not exist |
| `TOOLS = [...]` | The tool description sent to the model. It is a list because you can offer several tools |
| `"name"` | The name the model uses to ask for the tool. It matches the function name here, but only because we chose that |
| `"description"` | Plain English telling the model when to use the tool. The model reads it the way it reads instructions |
| `"parameters"` | A JSON schema for the arguments, similar to the Pydantic class in Concept 1 |
| `"additionalProperties": False` | The model may not add arguments that are not listed |
| `"strict": True` | The API forces the arguments to match the schema. As in Concept 1, a valid structure does not mean correct content |
| `conversation = [...]` | The conversation so far, as a list. It starts with the user's message and grows with each round |
| `responses.create(..., tools=TOOLS)` | Round 1. `create` is used instead of `parse` because the reply may be a tool call rather than a fixed schema |
| `conversation += response.output` | Adds everything the model returned, including its tool call, to the conversation. The API needs this in round 2 to match each result to its call |
| `for item in response.output:` | The model's output is a list of items. It may contain zero, one or several tool calls |
| `if item.type != "function_call": continue` | Skips anything that is not a tool call |
| `json.loads(item.arguments)` | Converts the JSON text `{"ticket_id":"T-101"}` into a Python `dict` |
| `if item.name == "get_ticket_status":` | **Your code chooses which function runs.** An unknown name gets an error, not a guess |
| `"type": "function_call_output"` | Wraps the result so the API knows it is a tool result |
| `"call_id": item.call_id` | Links the result to the call that asked for it |
| `json.dumps(result)` | Converts the Python `dict` back into JSON text |
| Round 2 `responses.create(...)` | Sends the whole conversation back. The model now writes the answer |
| `response.output_text` | The model's final text answer |

### Observed result (Claude's test run, two runs)

```
Model asks for: get_ticket_status {"ticket_id":"T-101"}
Our code returns: {'ticket_id': 'T-101', 'status': 'open', 'assigned_to': 'access team'}
Answer: Ticket T-101 is open and assigned to the access team.
```

Both runs asked for the same tool with the same argument. One answer used bold text, and one did not.

### Observed results (three runs)

| Run | Question | Tool call | Our code returned | Answer |
|---|---|---|---|---|
| 1 | My ticket T-101 | `get_ticket_status {"ticket_id":"T-101"}` | status `open`, `access team` | Correct |
| 2 | Ticket T-999 | `get_ticket_status {"ticket_id":"T-999"}` | `{"error": "ticket not found"}` | Said it could not find the ticket. It did not invent a status |
| 3 | How do I reset my password? | **None** | Nothing | Generic advice ("Forgot password?" on the sign-in page) |

What this shows:

| Observation | Meaning |
|---|---|
| The model chose by itself whether to call a tool | Offering a tool does not force the model to use it. The model decides, and your code only sees the calls it makes |
| Run 2: the error went back to the model as data | An error result is still a result. The model reported it honestly here, but nothing in the code guarantees that |
| Run 3: no tool call, so the loop did nothing, yet round 2 still ran | The round 1 reply already contained the answer. Round 2 was a second paid call that was not needed. A real program only sends a second round when there were tool calls |
| Run 3: the advice did not come from any of our systems | The model answered from its general training, not from your organisation's actual password process. With no tool to call, it can still sound confident |
