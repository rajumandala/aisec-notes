## What an agent framework is

In Concepts 3 and 4, you wrote everything by hand: the tool descriptions, the loop, running each tool, adding results to the conversation, and the step limit. That took about 100 lines.

An **agent framework** is a library that does this for you. You write the tool functions and the instructions; the framework runs the loop.

Examples: the **OpenAI Agents SDK**, the **Claude Agent SDK**, **LangGraph**, **CrewAI** and **Pydantic AI**. They differ in detail, but they all do the same jobs underneath. LangChain and LangGraph have their own note, Concept 11a.

## Example

File: `src/ai_appsec/agents_sdk_example.py`, using the OpenAI Agents SDK (version 0.23.1). It is the owner check from Concept 3, rewritten.

```python
@dataclass
class Session:
    signed_in_user: str

@function_tool
def get_ticket(ctx: RunContextWrapper[Session], ticket_id: str) -> dict:
    """Read a helpdesk ticket by its ID."""
    ticket = TICKETS.get(ticket_id)
    if ticket is None or ticket["owner"] != ctx.context.signed_in_user:
        return {"error": "ticket not found"}
    return {...}

agent = Agent(name="Helpdesk assistant", instructions="...", model="gpt-6-luna", tools=[get_ticket])

result = Runner.run_sync(agent, "What is the status of T-101 and T-102?",
                         context=Session(signed_in_user="asha@example.com"), max_turns=6)
```

| Line | Meaning |
|---|---|
| `@function_tool` | Turns the function into a tool. The framework builds the tool description from the docstring and the argument types |
| `ctx: RunContextWrapper[Session]` | Your own data for this run. It is **not** sent to the model, so this is the right place for the signed-in user |
| `Agent(...)` | Instructions, model and tools together |
| `Runner.run_sync(...)` | Runs the whole agent loop from Concept 4 |
| `max_turns=6` | The step limit |

Output, for Asha:

```
- T-101: Open — reports a VPN authentication failure after a password change.
- T-102: Not found.
```

About 25 lines instead of 100. The owner check still works, because it is in your function.

## What the framework decides for you

When you wrote the loop, you saw every decision. With a framework, the decisions still exist, but they are hidden in its **default settings**. These are the defaults I found in the OpenAI Agents SDK, version 0.23.1:

| Question | Default | Why it matters |
|---|---|---|
| How many steps? | `max_turns` is **10**. When it is exceeded, the framework raises a `MaxTurnsExceeded` error | You must catch it and tell the user honestly that the task did not finish (Concept 4). It counts steps, not tokens or money |
| What does the model see when a tool fails? | "An error occurred while running the tool. **Please try again.**" | This message invites the model to retry, which is how the endless retry in Concept 4 started |
| Are tool calls approved by a person? | No. `needs_approval` is `False` unless you set it | Actions with consequences run without asking |
| Is a record of each run sent anywhere? | **Yes. Tracing is on**, and runs are sent to OpenAI's tracing service | See below |
| Does that record include the data? | **Yes.** `trace_include_sensitive_data` is true by default | Model inputs and outputs, and tool inputs and outputs, are included |
| Where does the tool description come from? | The function's docstring | A careless docstring becomes an instruction to the model |

### Tracing

**Tracing** records each step of a run (model calls, tool calls, their inputs and outputs) so that you can debug it in a web dashboard. That is useful. But by default here, every ticket text, every tool result and every answer is copied to a third-party service, which may not be allowed for your data.

To turn it off, set this environment variable:

```
OPENAI_AGENTS_DISABLE_TRACING=true
```

or keep tracing on without the data by setting `trace_include_sensitive_data` to false in `RunConfig`. Decide this before the first real data goes through the system.

## What a framework does not change

The framework runs the loop. It does not make your design safe.

| Still your job | Example |
|---|---|
| Authorisation inside each tool | The owner check in `get_ticket` |
| Identity from a trusted source, not from the model | `context=Session(signed_in_user=...)` |
| Treating tool results, documents and other agents' output as untrusted | Concepts 3, 7 and 9 |
| Limits on cost, not only steps | Track tokens yourself |
| Approval for actions with consequences | Set `needs_approval` on those tools |

Framework features such as "guardrails" are useful extra checks, but most of them are model-based classifiers: detection (level 3 in Concept 10), not design.

## Reviewing a system built on a framework

| Question | Why |
|---|---|
| Which framework and which version? | Defaults change between versions. Pin the version, as with any dependency |
| What are the step, time and cost limits? | The default may be too high, or missing |
| What happens when a limit is reached? | An unhandled error may leave work half done with no message to the user |
| Is tracing on? Where is it sent, and does it include data? | It may copy all user data to a third party |
| Which tools need approval? | The default is usually none |
| What does the model see when a tool fails? | The default text may encourage retries, or leak error details |
| How many extra packages did the framework bring in? | Each one is part of your supply chain |

## Summary

| Lesson | Example |
|---|---|
| A framework runs the agent loop for you | 25 lines instead of 100 |
| Its default settings make security decisions for you | Step limit 10, no approvals, tracing on |
| Read the defaults before using it with real data | Tracing sends inputs and outputs to OpenAI by default |
| Your own security checks still belong in your code | The owner check in `get_ticket` |
| Keep the signed-in user in the run context, not in model arguments | `ctx.context.signed_in_user` |
