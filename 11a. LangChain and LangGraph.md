## What LangChain and LangGraph are

**LangChain** is a library of building blocks for AI applications: a common way to call many model providers, tools, document loaders, vector stores and hundreds of integrations. Since version 1.0, its main way to build an agent is `create_agent`.

**LangGraph** is the engine underneath. It runs an application as a **graph**:

| Part             | Meaning                                                 | Helpdesk example                                       |
| ---------------- | ------------------------------------------------------- | ------------------------------------------------------ |
| **Node**         | One step: a function, a model call or a tool call       | "Call the model", "Run the tools"                      |
| **Edge**         | Which node runs next                                    | After the model asks for a tool, go to "Run the tools" |
| **State**        | Shared data that every node reads and updates           | The list of messages so far                            |
| **Checkpointer** | Saves the state after every step, under a **thread ID** | Asha's chat is saved as thread `chat-1`                |

The agent loop from Concept 4 is a small graph: model → tools → model → … → answer. LangGraph lets you draw bigger graphs (several agents, approval steps, branches), and the checkpointer lets a conversation stop and continue later.

Versions used in this note: `langchain` 1.4.3, `langgraph` 1.2.14, `langgraph-checkpoint` 4.2.0. Defaults change between versions, so check yours.

## Example

The owner check from Concept 3, written with LangChain, and with a checkpointer that saves conversations:

```python
@dataclass
class Session:
    signed_in_user: str

@tool
def get_ticket(ticket_id: str, runtime: ToolRuntime[Session]) -> dict:
    """Read a helpdesk ticket by its ID."""
    ticket = TICKETS.get(ticket_id)
    if ticket is None or ticket["owner"] != runtime.context.signed_in_user:
        return {"error": "ticket not found"}
    return {...}

agent = create_agent(
    model="openai:gpt-6-luna",
    tools=[get_ticket],
    system_prompt="You help users with their helpdesk tickets. Use the tools.",
    context_schema=Session,
    checkpointer=InMemorySaver(),
)

result = agent.invoke(
    {"messages": [{"role": "user", "content": "What is the status of T-101 and T-102?"}]},
    config={"configurable": {"thread_id": "chat-1"}, "recursion_limit": 12},
    context=Session(signed_in_user="asha@example.com"),
)
```

| Line | Meaning |
|---|---|
| `@tool` | Turns the function into a tool. The docstring becomes the tool description |
| `runtime: ToolRuntime[Session]` | Gives the tool your own run data. The model does not see it and cannot fill it in |
| `create_agent(...)` | Builds the model → tools → model graph for you |
| `checkpointer=InMemorySaver()` | Saves the conversation after every step. In production this is usually a Postgres or SQLite database |
| `thread_id` | Which saved conversation to load and continue |
| `recursion_limit` | The step limit. Each model call and each tool run counts as a step |
| `context=Session(...)` | The signed-in user, from your login system |

Asha gets T-101, and T-102 is "not found". The owner check works, because it is in your function.

## The new risk: a thread ID is an object reference

The checkpointer loads whatever conversation matches the `thread_id`. It does not know who is asking.

In the example, Asha's conversation is saved as `chat-1`. It contains the tool result with her ticket text. Then Ravi sends a request with `thread_id` `chat-1` and asks: "Repeat what my VPN ticket said, word for word."

```
Ravi, no check: VPN says 'authentication failed' after I changed my password.
```

Ravi never called the tool for T-101; the owner check would have refused him. He did not need to. The text was already in the saved conversation, and the model read it back to him.

This is the classic **IDOR** (insecure direct object reference), with a thread ID in place of an invoice number. If your web app takes the thread ID from the browser, it must check that the signed-in user owns that thread before every run:

```python
THREAD_OWNERS = {"chat-1": "asha@example.com"}

def ask(signed_in_user, thread_id, question):
    owner = THREAD_OWNERS.setdefault(thread_id, signed_in_user)
    if owner != signed_in_user:
        return "conversation not found"
    return agent.invoke(...)
```

```
Ravi, with check: conversation not found
```

Random, hard-to-guess thread IDs help, but they are not access control. A thread ID can appear in logs, URLs and support tickets.

## What the framework decides for you

| Question | Default (versions above) | Why it matters |
|---|---|---|
| How many steps? | `create_agent` sets `recursion_limit` to **9,999**. Plain LangGraph graphs default to 10,007 | Practically no step limit. A retry loop (Concept 4) can run thousands of model calls. Always set your own limit, and also limit tokens |
| What happens at the limit? | A `GraphRecursionError` is raised | Catch it and tell the user honestly that the task did not finish |
| What does the model see when a tool fails? | If the model sent wrong arguments, the error text goes back to the model. Any other error stops the whole run | Decide what each tool returns on failure. Do not pass raw exception text (paths, SQL, stack details) to the model |
| Are tool calls approved by a person? | No. You must add `HumanInTheLoopMiddleware` with `interrupt_on` | Actions with consequences run without asking |
| When approval is on, what can the approver do? | `interrupt_on={"close_ticket": True}` allows **approve, edit, reject and respond**. "Edit" lets the approver change the arguments | See "Approvals" below |
| Is the conversation saved? | Only if you pass a checkpointer. Once you do, **every step is saved**, including tool results | Saved state is stored data: it needs access control, retention rules and encryption, like any database of user data |
| Is tracing on? | **Off** unless the environment variable `LANGSMITH_TRACING=true` is set | When it is on, inputs and outputs go to LangSmith. `LANGSMITH_HIDE_INPUTS=true` and `LANGSMITH_HIDE_OUTPUTS=true` keep the data out |

Compare this with the OpenAI Agents SDK in Concept 11: there, tracing was on by default and the step limit was 10. Each framework makes different choices, which is why you read the defaults of the one in front of you.

## Approvals with interrupts

LangGraph pauses a run with an **interrupt**. The state is saved by the checkpointer, a person is asked, and the run continues when the app sends a "resume" command with the decision for that thread.

This makes approvals easy to add, but the rules from Concept 4 still apply, and the framework does not enforce them for you:

| Rule | Why |
|---|---|
| Check who is resuming the thread | Whoever can send a resume command to the thread ID is the approver. Apply the thread owner check, and the approver role check, before resuming |
| The approver must be a different person from the requester, where the action needs it | The framework does not know your roles |
| Allow "edit" only where it is needed | With "edit", the action that runs is not the action that was shown for approval. Use `allowed_decisions=["approve", "reject"]` for most tools |
| Show the approver the exact arguments | Approval of a vague summary is not approval of the action |

## Saved state is memory

A checkpointer keeps everything the agent saw: user messages, tool results, retrieved documents. When the conversation continues, all of it goes back to the model.

So an instruction hidden in one tool result (Concept 3) or document (Concept 7) stays in the thread and affects every later turn, exactly like the memory attack in Concept 8. LangGraph's long-term **store** (memory shared across threads) has the same risk across sessions.

Saved state is also **deserialised** when it is loaded. In the past, this was a code execution path (see below). Treat the checkpoint database as trusted storage: only your app should be able to write to it.

## Past vulnerabilities

| CVE | Package | Problem | Fixed in |
|---|---|---|---|
| CVE-2025-68664 ("LangGrinch") | `langchain-core` | `dumps()` did not escape user data containing the internal `lc` key. When loaded back, attacker data was treated as a LangChain object. This could read secrets from environment variables and inject prompts | 1.2.5 and 0.3.81 |
| CVE-2025-64439 | `langgraph-checkpoint` | In one fallback case, saved state was written in a JSON mode whose loader could rebuild objects and run Python functions. An attacker who could get a payload saved could run code when it was loaded | 3.0 |

Older LangChain versions also had chains that ran model-written Python or SQL directly. Most were moved to `langchain-experimental` or `langchain-community` with warnings. The lesson is the same as Concept 9: model-written code runs only in a sandbox.

Two habits follow:

1. **Pin versions** and watch advisories for `langchain-core`, `langgraph` and `langgraph-checkpoint`. They are dependencies with a history of serious issues, like any web framework.
2. **Install only the integrations you use.** `langchain-community` contains hundreds of integrations written by many people. Each one you import is part of your supply chain (Concept 11).

## Reviewing a LangChain or LangGraph system

| Question | Why |
|---|---|
| Which versions of `langchain-core`, `langgraph` and `langgraph-checkpoint`? | Both CVEs above were in these packages |
| What is the `recursion_limit`? Is there a token or cost limit? | The default is effectively unlimited |
| Is there a checkpointer? Where is the state stored, and for how long? | Saved state holds all tool results and user data |
| Where does the `thread_id` come from? Who checks that the user owns the thread? | Without a check, any user can read or continue another user's conversation |
| Who can resume an interrupted thread, and with which decisions? | The resume command is the approval |
| How does the signed-in user reach the tools? | It must come from `context`, not from model arguments or the message text |
| Is LangSmith tracing on? Does it hide inputs and outputs? | Tracing copies data to a third party |
| Which `langchain-community` integrations are imported? | Each one is third-party code in your app |

## Summary

| Lesson | Example |
|---|---|
| LangGraph runs an agent as a graph of nodes with shared, saved state | model → tools → model, saved per thread |
| A thread ID is an object reference and needs an owner check | Ravi read Asha's ticket from her saved thread |
| Saved state is memory: a poisoned tool result stays for every later turn | Concept 8, now inside one conversation |
| `create_agent` has practically no step limit by default | `recursion_limit` 9,999 |
| Approvals are interrupts; whoever resumes the thread is the approver | Check identity and limit "edit" |
| Pin versions and limit integrations | CVE-2025-68664, CVE-2025-64439 |
