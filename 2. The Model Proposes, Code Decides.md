## The problem

In Concept 1, one line paged the on-call engineer:

```python
if triage.priority == "high":
    page_engineer()
```

The model chose `priority` from the ticket text, so the ticket writer effectively controlled the paging. A mouse mat request that mentioned "the CEO" and "financial loss" paged the engineer in 3 out of 3 runs.

## The principle

> **The model proposes. Code decides.**

- Model output is a **proposal**. Treat it like user input: useful, but not trusted.
- A decision with a cost (paging, approving, closing, deleting, paying) is made by ordinary code that is reviewed and tested.
- That code bases the decision on **trusted data** wherever possible.

Web security comparison: a website may hide the "Delete" button from normal users, but the server still checks permission when a delete request arrives, because anyone can send that request without the button. The model's recommendation is a convenience, not a security control.

## Three design rules

| Rule | Example |
|---|---|
| Untrusted input alone must not trigger a costly action | `priority == "high"` alone pages nobody |
| Untrusted input may send work to a person | A `high` proposal goes to an urgent queue, where a person checks it |
| The decision is predictable | The same inputs always give the same action, so it can be tested and checked later |

## Mixing trusted and untrusted inputs

The first fix paged only if monitoring had an active alert in the model's chosen category. It had a bypass: during a real hardware alert, the mouse mat ticket (category `hardware`) paged the engineer again. The category was untrusted, so matching it proved nothing.

> When a decision combines trusted and untrusted inputs, the untrusted part can still be attacked. The trusted part only limits **when** the attack works.

**Fix: give untrusted input the least powerful action.** This is called **least privilege**. Related tickets are attached to the active incident instead of paging anyone. Only monitoring can page.

```python
def decide_action(triage: TicketTriage, active_alerts: set[str]) -> str:
    if triage.priority == "high" and triage.category in active_alerts:
        return "attach to the active incident"
    if triage.priority == "high":
        return "urgent queue: a person checks the claimed impact"
    return "normal queue"
```

The model is still manipulated, but the damage is limited. Prompts have no equivalent of parameterised queries, so the working assumption is:

> **Assume anyone who controls the model's input can manipulate its output. Design so that a manipulated output does limited damage.**

## Separate facts from judgement

The model did two jobs at once. Separating them reduces the manipulation:

| Job | Example | Easy to manipulate? |
|---|---|---|
| Extract facts | "The requester says they cannot finish a CEO metric" | Hardly: the ticket really says it |
| Make a judgement | "So the priority is high" | Yes: persuasion works here |

The model now returns `impact_claims` (copied sentences) and no `priority`. Code sets the priority:

| Condition | Source | Priority |
|---|---|---|
| Active monitoring alert in this category | Monitoring (trusted) | high |
| 3 or more different signed-in users reported this category in the last hour | Ticket and login systems (trusted) | high |
| The ticket contains impact claims | Ticket text (untrusted) | medium |
| None of these | Not applicable | low |

A ticket writer can reach `medium` on their own, never `high`.

Security comparison: a code-scanning tool reports "possible SQL injection on line 42". That is a fact about the code. How urgently to fix it is decided by the team, using things the tool does not know, such as whether that page is on the public internet.

## Who may raise the priority

Asha's honest VPN ticket ("client demo at 3 pm") got `medium`. If it truly needs `high`, code cannot raise it from her sentence, because that is ticket text. Only two things can:

- **A person**, such as an analyst who checks the claim. The change is recorded with their name.
- **Code using data the requester cannot write.**

> **Trusted means the person whose claim you are checking cannot write the data.** It does not mean the system storing it is secure.

Asha's own Outlook calendar is not trusted for this check: she can add any event to it, so it is the same claim stored in a different place. Like a `"role": "admin"` value the user saved in their own profile, it is not trusted just because it was read back from your system.
