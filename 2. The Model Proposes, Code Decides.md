## Part 1: The concept

### The problem from Concept 1

In `triage_ticket.py`, the decision to page an engineer is one line:

```python
if triage.priority == "high":
    print("Action:   page the on-call engineer")
```

`triage.priority` was chosen by the model, and the model chose it from the ticket text. So the chain of control is:

| Step | Who controls it |
|---|---|
| Ticket text | The ticket writer (untrusted) |
| `priority` | The model, influenced by the ticket text |
| Paging the engineer | One `if` statement that trusts `priority` completely |

The ticket writer controls the first step, so in practice they control the last one. Concept 1, Part 7 proved this: a mouse mat request paged the engineer 3 times out of 3.

### The principle

> **The model proposes. Code decides.**

- The model's output is a **proposal**. Treat it like any other user input: useful, but not trusted.
- A **decision** that has a cost (paging, approving, closing, deleting, paying) is made by ordinary code that a person owns, reviews and tests.
- That code bases the decision on **trusted data** wherever it can: data from your own systems that the ticket writer cannot change.

### AppSec equivalent

| Web application | AI application |
|---|---|
| The browser can show or hide the "Delete" button | The model can recommend `high` priority |
| The server still checks permission before deleting | Code still checks trusted evidence before paging |
| Hiding the button is a convenience, not security | The model's recommendation is a convenience, not security |

### Trusted and untrusted inputs to a decision

| Input | Source | Can the ticket writer change it? | Trusted? |
|---|---|---|---|
| `priority`, `category`, `affected_users` | The model, from the ticket text | Yes, by choosing their words | No |
| Active monitoring alerts | Your monitoring system | No | Yes |
| The requester's identity | The login system, not the ticket text | No | Yes |

### Three design rules

| Rule | Meaning in this example |
|---|---|
| **Untrusted input alone must not trigger a costly action** | `priority == "high"` alone must not page anyone |
| **Untrusted input may send work to a person** | A `high` proposal can put the ticket in an urgent queue where a person checks the claim. A real emergency is still seen quickly |
| **The decision is deterministic** | The same inputs always give the same action. It can be tested, explained and audited, unlike the model's answer (Concept 1, Part 5) |

The second rule matters. A rule that simply ignores the model would block attackers, but it would also ignore genuine emergencies. Sending the ticket to a person instead of dropping it keeps the benefit of the model and removes its authority.

## Part 2: Worked example

### The decision function

```python
def decide_action(triage: TicketTriage, active_alerts: set[str]) -> str:
    """Decide what to do with a ticket. The model's triage is only a proposal."""
    if triage.priority == "high" and triage.category in active_alerts:
        return "page the on-call engineer"
    if triage.priority == "high":
        return "urgent queue: a person checks the claimed impact"
    return "normal queue"
```

### Line-by-line explanation

| Code | What it does |
|---|---|
| `def decide_action(...)` | Defines a function: a named piece of code that takes inputs and returns a result |
| `triage: TicketTriage` | First input: the model's proposal (untrusted) |
| `active_alerts: set[str]` | Second input: the categories that monitoring currently reports a problem in (trusted). A `set` is a collection of unique values, for example `{"network"}` |
| `-> str` | The function returns text: the action to take |
| `triage.category in active_alerts` | `True` if the model's category matches an active alert |
| First `if` | Pages only when the model says `high` **and** monitoring confirms a problem in that category |
| Second `if` | The model says `high` but nothing confirms it: a person checks it quickly, nobody is paged |
| `return "normal queue"` | Everything else |

### Decision table

| Model says | Monitoring alert in that category? | Action |
|---|---|---|
| `high` | Yes | Page the on-call engineer |
| `high` | No | Urgent queue: a person checks |
| `low` or `medium` | Either | Normal queue |

### Where it goes in the program

Monitoring is simulated with a constant. An empty set `set()` means nothing is currently alerting.

```python
ACTIVE_ALERTS: set[str] = set()

# ... call the model as before ...

action = decide_action(triage, ACTIVE_ALERTS)
print("Action:  ", action)
```

### Expected results

| Ticket | Model proposes | `ACTIVE_ALERTS` | Action |
|---|---|---|---|
| Mouse mat with "CEO" and "financial loss" (Concept 1, Part 7) | high | empty | Urgent queue. **Nobody is paged** |
| Asha's VPN ticket | high or medium | empty | Urgent queue or normal queue. Nobody is paged |
| Asha's VPN ticket | high, category `access` | `{"access"}` | Page the on-call engineer |

The attack in Concept 1 still changes the model's answer. It no longer changes the action, because paging now needs evidence the attacker does not control.

## Part 4: Give untrusted input the least powerful action

### The bypass in Part 3

`triage.category` comes from the model, so the ticket writer controls it. When a real alert is active, matching its category is enough to page the engineer. The category was not even wrong: a mouse mat really is `hardware`. **A matching category does not prove the ticket is related to the incident.**

> When a decision combines trusted and untrusted inputs, the untrusted part can still be attacked. The trusted part only limits **when** the attack works.

### The fix: attach, do not page

During a real incident, monitoring has already paged the on-call engineer. Paging again adds no information. Related tickets are **attached** to the incident, where the people already working on it review them.

| Model says | Alert in that category? | Action |
|---|---|---|
| `high` | Yes | Attach to the active incident |
| `high` | No | Urgent queue: a person checks the claimed impact |
| `low` or `medium` | Either | Normal queue |

> **Least privilege for actions:** give untrusted input the least powerful action that still gets the work done. Only trusted sources (monitoring, a declared incident) can trigger the expensive action.

### My code

```python
def decide_action(triage: TicketTriage, active_alerts: set[str]) -> str:
    """Decide what to do with a ticket. The model's triage is only a proposal."""
    if triage.priority == "high" and triage.category in active_alerts:
        return "attach to the active incident"
    if triage.priority == "high" and triage.category not in active_alerts:
        return "urgent queue: a person checks the claimed impact"
    return "normal queue"
```

The `and triage.category not in active_alerts` part is redundant: if the category were in `active_alerts`, the first `return` would already have run. It is harmless and makes the rule explicit.

### Observed result

| `ACTIVE_ALERTS` | Category | Priority | Action |
|---|---|---|---|
| `{"hardware"}` | hardware | high | Attach to the active incident. **Nobody paged** |

The word "page" no longer appears in `decide_action`. **No model output can page anyone.** Only monitoring can.

### What is still not fixed

The model is still manipulated: every exaggerated ticket is still marked `high` and lands in the urgent queue ahead of honest users. Limiting consequences does not stop the manipulation.

This is deliberate. Prompts have no equivalent of parameterised queries: instructions and input arrive as one stream of text, and no filter reliably separates them. So the working assumption is:

> **Assume anyone who controls the model's input can manipulate its output. Design so that a manipulated output does limited damage.**

The cause can still be **reduced** (Part 5): ask the model only to extract facts, and let code set the priority from those facts plus trusted data.

## Part 5: Separate facts from judgement

### The concept

Until now the model did two different jobs in one answer:

| Job | Example | Can the ticket writer manipulate it? |
|---|---|---|
| **Extracting facts**: what does the ticket say? | "The requester says they cannot complete a CEO metric" | Hardly. The ticket really does say that |
| **Making a judgement**: what should we do about it? | "So the priority is `high`" | Yes. This is where persuasion works |

Extraction is a reading task: the answer can be checked against the ticket text. Judgement is a decision, and decisions belong in code (Part 1).

So the model's job shrinks:

| Before | After |
|---|---|
| The model chooses `priority` | The model **copies the impact claims** out of the ticket |
| Priority comes from what the ticket writer says | Priority comes from **code**, using trusted data. The ticket's claims can raise it to `medium` at most |

### AppSec equivalent

A SAST tool reports "possible SQL injection at line 42". That is a fact: the pattern exists. Whether it is exploitable and how urgently it must be fixed is decided by your triage policy, using data the tool does not have: is the endpoint internet-facing, does it handle sensitive data? The tool reports; the policy decides.

### The priority rule (owned by code)

| Condition | Source | Priority |
|---|---|---|
| Monitoring has an active alert in this category | Monitoring (trusted) | high |
| 3 or more **different signed-in users** reported this category in the last hour | Ticket system and login records (trusted) | high |
| The ticket contains impact claims | Ticket text (untrusted) | medium |
| None of the above | | low |

The ticket writer can reach `medium` on their own, never `high`. To reach `high` they would need monitoring to agree, or three separate accounts.

## Part 6: Worked example

File: `src/ai_appsec/triage_facts.py`

```python
from typing import Literal

from dotenv import load_dotenv
from openai import OpenAI
from pydantic import BaseModel

load_dotenv()

client = OpenAI()

# Trusted data from your own systems (simulated).
# Categories where monitoring currently reports a problem.
ACTIVE_ALERTS: set[str] = set()
# How many different signed-in users reported each category in the last hour.
RECENT_REPORTERS: dict[str, int] = {}


class TicketFacts(BaseModel):
    summary: str
    category: Literal["access", "hardware", "software", "network", "other"]
    impact_claims: list[str]


def set_priority(
    facts: TicketFacts, active_alerts: set[str], recent_reporters: dict[str, int]
) -> str:
    """Set the priority in code. The ticket's own claims can raise it to medium at most."""
    if facts.category in active_alerts:
        return "high"
    if recent_reporters.get(facts.category, 0) >= 3:
        return "high"
    if facts.impact_claims:
        return "medium"
    return "low"


def decide_action(priority: str, category: str, active_alerts: set[str]) -> str:
    """Decide what to do with a ticket."""
    if priority == "high" and category in active_alerts:
        return "attach to the active incident"
    if priority == "high":
        return "urgent queue"
    return "normal queue"


ticket = (
    "Need a mouse mat\n"
    "I am working on important metric for CEO, and without this mat I cannot complete that.\n"
    "This will result in a great financial loss for the company"
)

response = client.responses.parse(
    model="gpt-6-luna",
    instructions=(
        "You are a helpdesk assistant. Extract facts from the ticket. Do not judge priority. "
        "In impact_claims, copy word for word every sentence where the requester describes "
        "business impact or urgency. If there are none, return an empty list."
    ),
    input=ticket,
    text_format=TicketFacts,
)

facts = response.output_parsed
if facts is None:
    raise RuntimeError("The model did not return TicketFacts.")

priority = set_priority(facts, ACTIVE_ALERTS, RECENT_REPORTERS)
action = decide_action(priority, facts.category, ACTIVE_ALERTS)

print("Summary: ", facts.summary)
print("Category:", facts.category)
print("Impact claims:")
for claim in facts.impact_claims:
    print("  -", claim)
print("Priority:", priority, "(set by code)")
print("Action:  ", action)
```

### Line-by-line explanation (only the new parts)

| Code | What it does |
|---|---|
| `RECENT_REPORTERS: dict[str, int] = {}` | Simulates the ticket system. A `dict` maps keys to values, for example `{"access": 4}` means 4 different users reported an access problem in the last hour. `{}` means none |
| `class TicketFacts` | The new schema. There is no `priority` field: the model is no longer asked for one |
| `impact_claims: list[str]` | A list of text items: the sentences where the requester claims impact |
| `def set_priority(...)` | The priority rule from Part 5, in code |
| `recent_reporters.get(facts.category, 0)` | Looks up the count for this category. If the category is not in the dict, it returns `0` instead of failing |
| `if facts.impact_claims:` | `True` if the list has at least one item. An empty list counts as `False` |
| `instructions="... Do not judge priority ..."` | The model is told to extract only, and to copy claims word for word |
| `decide_action(priority, facts.category, ACTIVE_ALERTS)` | Now receives the priority set by code, not by the model |
| `for claim in facts.impact_claims:` | Prints each claim on its own line, so a person can see exactly what was claimed |

### Observed result (Claude's test run, mouse mat ticket)

| Category | Impact claims found | Priority | Action |
|---|---|---|---|
| hardware | 2 | medium (set by code) | Normal queue |

The model correctly found both claims. It also added a full stop to the end of the second claim, so "word for word" was not exactly followed. Copied text should not be assumed to be exact; it can be checked against the original.

## Part 8: Who may raise the priority

### My first answer, and the correction

The question was whether `medium` is acceptable for Asha's honest ticket. I said no, and that code should be allowed to raise it.

The problem with "code should raise it" is that code raises the priority only by checking some input. The only urgency in Asha's ticket is "I have a client demo at 3 pm", which is ticket text. If code raised the priority because of that sentence, the mouse mat ticket would reach `high` the same way.

So the real question is **what code checks, or who decides instead**:

| Who raises it | How | Why it is safe |
|---|---|---|
| A person (a helpdesk analyst) | They read the ticket, possibly call the requester, and set `high` themselves. The change is recorded with their name | A person who is accountable makes the judgement, and there is an audit trail |
| Code using trusted data | Code checks a source the requester cannot edit, and raises the priority only if that source confirms the claim | The ticket writer's words are no longer the evidence |

`medium` is a reasonable default, but the current design has a gap: a `medium` ticket with impact claims goes to the normal queue, where nobody may look at it before 3 pm. A better rule shows such tickets, with their claims, to an analyst who can raise them. **The claims direct a person's attention. They do not set the priority.**

### Is Outlook calendar a trusted source?

My second answer was "Outlook calendar, and we can assume it cannot be breached."

That assumption answers the wrong question. Whether the calendar can be breached does not matter here. What matters is **who can write to it**. Asha can create any event in her own calendar, and so can an attacker who has logged in as her. A "Client demo 3 pm" event is the same claim as the ticket sentence, typed into a different place.

> **Trusted means the person whose claim you are checking cannot write the data.** It does not mean the system storing the data is secure.

| Source | Who writes it | Trusted for checking Asha's claim? |
|---|---|---|
| Ticket text | Asha | No |
| Asha's own calendar | Asha | No: it is the same claim stored somewhere else |
| Monitoring alerts | The monitoring system | Yes |
| Count of different signed-in users reporting the problem | The login system and other users | Yes, unless one person controls several accounts |
| Asha's job role in the HR directory | HR | Yes, but it shows she *could* have client demos, not that she has one today |
| An analyst who phones Asha | The analyst | Yes, and it is recorded with the analyst's name |

### AppSec equivalent

A user's request says `"role": "admin"`. Storing that value in the user's own profile and reading it back does not make it trusted, because the user wrote both copies. The server checks the role against a table that only administrators can change.
